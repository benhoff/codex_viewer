# Search API follow-up requirements

Status: proposed

Validated against the hosted API: 2026-09-05

Current API reference: [search-api.md](search-api.md)

## Purpose

This document records the changes needed to make the Search API reliable for exhaustive, reproducible repository research. It is based on live validation of the API, including the VDONE frame-semantics investigation.

The existing API already supports useful evidence discovery. The remaining gaps are primarily about proving that a search was complete, preventing a research session from finding its own generated text, retrieving large turns efficiently, and giving captured evidence a stable identity.

## Confirmed baseline

The following capabilities were verified and should be preserved:

- Canonical `repository_id` filtering, repository discovery, and repository aliases.
- Field-scoped search over `prompt`, `response`, `activity`, `commands`, `paths`, `commit_ids`, and `tool_output`.
- `exact`, `phrase`, `any`, and `all` query modes.
- Project, source, branch, and time filtering and facets.
- Batched searches using one authentication and ACL evaluation context.
- Coverage and freshness metadata that exposes indexed, current, stale, failed, and pending sessions and turns.
- Deterministic result ordering and cursor-based search pagination.

These features are sufficient for positive evidence discovery. They are not yet sufficient to make a definitive negative or corpus-wide claim while indexing is incomplete or changing.

## Required changes

### P0: Reject unsupported parameters

#### Observed behavior

Unknown query parameters are silently ignored. In live tests, both `exclude_session_id` and `activity_limit` received successful responses even though neither restriction was applied. The ignored parameters were absent from the echoed filters.

#### Risk

A caller can believe that an evidence constraint was enforced when the server actually searched or returned a broader data set. This is especially dangerous for automated research and validation tooling.

#### Requirement

Every endpoint must reject unknown query parameters and request-body properties with HTTP `422`. The structured error must identify the unsupported name and list or link to the allowed names.

This rule applies to:

- `GET /api/v1/search`
- `POST /api/v1/search/batch`, including both top-level and per-query properties
- `GET /api/v1/projects`
- Complete-turn and activity retrieval endpoints

Recognized parameters must be included in the response's normalized or echoed request metadata. A parameter must never be accepted and then ignored.

#### Acceptance tests

1. A misspelled or unknown parameter returns `422`, not `200`.
2. An unknown field in one batch query identifies the query index and offending field.
3. Every accepted filter is represented in the normalized request metadata.
4. Cursor requests reject parameters that conflict with the cursor-bound query.

### P0: Exclude the active research session

#### Observed behavior

The API has no supported session-exclusion filter. Searches can therefore rediscover prompts, responses, commands, and tool output generated by the investigation itself. This creates self-referential matches and can make later searches appear to corroborate earlier conclusions.

#### Requirement

Add an exact session-exclusion filter:

```text
exclude_session_id=<session-id>
```

The parameter should be repeatable to exclude more than one session, with a documented maximum. It must be supported consistently by normal search and each batch query.

Excluded sessions must not contribute to:

- Results
- Facets
- Coverage totals for the eligible corpus
- Pagination cursors

The response must echo the normalized exclusion list. Cursors must be cryptographically bound to it.

#### Acceptance tests

1. A known unique token returns its source session without the filter.
2. The same query excludes that result when its session ID is supplied.
3. Facets and coverage totals decrease consistently when an otherwise eligible session is excluded.
4. Reusing a cursor with a different exclusion list is rejected.
5. Batch and non-batch executions of the same filtered query return equivalent results.

### P0: Provide a stable searchable snapshot

#### Observed behavior

Coverage changed during one multi-query investigation as reindexing progressed. The batch API documents an ACL snapshot, but responses provide no reusable corpus or index-generation token. Separate requests therefore cannot prove that they searched the same indexed state.

#### Requirement

Return an opaque `snapshot_id` for project discovery, search, batch search, and evidence retrieval. A caller must be able to provide that identifier on subsequent requests to pin the searchable corpus and index generation.

At minimum, snapshot metadata must include:

- `snapshot_id`
- Creation and expiration times
- Corpus or index generation identifiers
- Coverage and freshness state at snapshot creation
- Relevant normalization/index schema versions

All queries in a batch must use one corpus snapshot, not only one authentication or ACL evaluation context.

A snapshot pins corpus membership and indexed content for reproducibility. Current authorization must still be enforced on every request; a snapshot must never preserve access after permission is revoked.

If a snapshot is invalid or expired, the server must return an explicit `409` or `410`. It must not silently fall back to current data.

#### Acceptance tests

1. The first query returns a reusable snapshot identifier.
2. Repeating the query with that identifier returns the same eligible-corpus counts, ordering, and content while live indexing advances.
3. An unpinned query may observe the newer generation.
4. Every query in a batch reports the same snapshot identifier.
5. Expired snapshots fail explicitly.
6. Revoking repository access prevents use of a previously issued snapshot.

Snapshot stability does not imply completeness. A snapshot with pending, stale, or failed sessions must continue to report those limitations, and a no-match result against it must not be described as exhaustive.

### P0: Define and reconcile project count semantics

#### Observed behavior

For repository `add45d4bd2144a7df9e91f3004b48614`, project discovery returned a GitHub project with `session_count=135` and a local-path project with `session_count=9`. Repository-scoped search coverage reported 135 total sessions, partitioned as 126 GitHub plus 9 local.

This makes the first project's count appear repository-aggregated while the second appears project-specific. That conflicts with a straightforward interpretation of `session_count` as a per-project count.

#### Requirement

Define every count as either project-scoped, source-scoped, or repository-scoped. Prefer:

- `session_count`: distinct sessions assigned to that exact `project_id`
- `repository_session_count`: distinct sessions across the canonical repository, when useful
- Source counts: distinct sessions in the named source within the stated scope

If a session can belong to multiple projects or sources, expose distinct totals and overlap explicitly rather than relying on sums.

Project discovery and search coverage must use the same identity and deduplication rules.

#### Acceptance tests

1. Filtering coverage by one `project_id` equals that project's `session_count`.
2. Mutually exclusive project counts sum to the repository's distinct session total.
3. If project sets overlap, the API reports the distinct repository total and documents the overlap.
4. Source totals reconcile with their documented scope.
5. Project and repository timestamps use the same defined aggregation rules.

### P1: Add selective, paginated activity retrieval

#### Observed behavior

Complete-turn retrieval currently returns activity as an all-or-nothing collection. A live request with `activity_limit=1` returned all 110 activity events because the unsupported parameter was silently ignored.

#### Requirement

Add a dedicated activity endpoint, for example:

```text
GET /api/v1/sessions/{session_id}/turns/{turn_id}/activity
```

It should support:

- `limit` with a documented bounded range
- Opaque cursor pagination
- Activity kind or event-type filters
- Tool-name filtering
- Optional event-index or time bounds

The response must provide:

- `total_count` for the filtered activity set
- `returned_count`
- `next_cursor`
- First and last returned event indexes
- The applicable `snapshot_id` and content identity

Ordering must be stable and chronological, with an immutable tie-breaker. Cursors must bind all filters, authorization scope, and the snapshot.

The existing complete-turn `include=activity` behavior may remain for compatibility, but clients must have a bounded way to retrieve large activity histories.

#### Acceptance tests

1. `limit=1` returns exactly one event and a continuation cursor when more events exist.
2. Paging through a 110-event turn returns exactly 110 unique events with no gaps or duplicates.
3. Tool and event-type filters return only matching activity.
4. A cursor cannot be reused with different filters or a different snapshot.
5. Unsupported filters return `422`.

### P1: Add immutable content identity

#### Observed behavior

Complete-turn JSON exposes no digest, ETag, content version, or normalization version. An evidence reference can therefore identify a session and turn, but cannot prove that the normalized captured content is byte-for-byte the same content later retrieved.

#### Requirement

Return a stable identity for normalized evidence content in both search hits and complete retrieval responses:

```json
{
  "content_digest": "sha256:<hex>",
  "normalization_version": "<version>",
  "content_version": "<opaque-version>"
}
```

The API specification must define the canonical serialization and exact digest scope. Volatile presentation data such as signed links, retrieval timestamps, and current coverage must not alter the content digest.

If activity is retrieved separately, expose both a turn-content digest and an activity-collection digest. HTTP `ETag` and conditional `If-None-Match` retrieval should use the same identity where practical.

This is an immutable identity for a particular normalized representation, not a claim that upstream source records can never be corrected or reimported.

#### Acceptance tests

1. A search hit and complete-turn retrieval report the same digest for the same digest scope.
2. Repeated retrieval of unchanged content produces the same digest.
3. Changing only links or retrieval metadata does not change the digest.
4. Correcting, reimporting, or renormalizing evidence changes either the digest or the normalization version as specified.
5. Conditional retrieval with the current ETag returns `304` when supported.

### P1: Add a dedicated patch-content field

#### Observed behavior

`paths` can isolate file names, while `activity` and `tool_output` can contain patch text mixed with unrelated events. There is no field that searches only the content of submitted or applied patches.

#### Requirement

Add `patches` to the searchable-field enum and index normalized patch content separately from paths and general activity.

Patch matches must:

- Report `matched_field=patches`
- Return bounded chunks with offsets under the existing chunk contract
- Preserve repository ACL behavior
- Participate in `exact`, `phrase`, `any`, and `all` modes
- Work consistently with facets, batch search, pagination, and snapshots

The normalization contract should state whether headers, context lines, removed lines, added lines, and tool-generated patch status messages are indexed.

#### Acceptance tests

1. A token present only in patch content is found with `fields=patches`.
2. The same token is not attributed to `paths` unless it also occurs in a path.
3. Patch chunks identify whether text came from an addition, deletion, header, or context when that distinction is available.
4. Patch-only results remain stable across pagination and batch execution.

## Cross-cutting contract rules

All new capabilities must follow these rules:

- Responses echo the fully normalized request, including defaults that materially affect result interpretation.
- Unknown or inapplicable parameters fail explicitly.
- Batch and single-query behavior remain semantically equivalent.
- Pagination cursors bind the normalized query, filters, repository scope, exclusions, authorization context, and snapshot.
- Current ACL checks can only reduce access to a snapshot; cached state must never broaden access.
- Coverage distinguishes repository discovery from indexed completeness.
- A no-match result is suitable for an exhaustive claim only when the pinned eligible corpus reports no pending, stale, failed, or otherwise unsearched content.
- Errors are machine-readable and distinguish invalid input, cursor mismatch, snapshot expiration, authorization failure, and incomplete indexing.

## Evidence-grade response record

For each research query, clients need enough server-provided data to retain this manifest:

```json
{
  "normalized_query": {},
  "repository_id": "<canonical-id>",
  "excluded_session_ids": [],
  "snapshot_id": "<opaque-id>",
  "coverage": {},
  "retrieval": {},
  "result_content_digests": []
}
```

This can be assembled from ordinary responses; a separate export endpoint is optional. The important requirement is that all values are authoritative, explicit, and consistent across the request set.

## Operational gate for exhaustive claims

The API should expose or document a simple machine-testable readiness condition. A repository snapshot is exhaustive only when all of the following are true for its eligible corpus:

```text
sessions_pending = 0
sessions_stale = 0
sessions_failed = 0
turns_pending = 0
turns_stale = 0
turns_failed = 0
```

If other states can make content unsearchable, they must be included in this gate. The response should ideally expose a derived `exhaustive_ready` boolean plus structured reasons, while retaining the underlying counts.

During the validation run, repository coverage was 124 of 135 sessions current and 1,537 of 1,744 turns current, with 11 sessions pending. Positive matches were usable, but a definitive no-match or repository-wide conclusion was not yet supportable.

## Recommended implementation order

1. Enforce strict parameter validation first, so later feature tests cannot pass falsely.
2. Implement session exclusion and reconcile project counts.
3. Add corpus snapshots and the exhaustive-readiness contract.
4. Add content digests and versions.
5. Add paginated activity retrieval.
6. Add the dedicated `patches` field.
7. Run the complete acceptance matrix against single search, batch search, pagination, project discovery, and full evidence retrieval.

## Definition of done

The follow-up is complete when an evidence collector can:

1. Resolve a repository unambiguously.
2. Exclude its own active research sessions.
3. Pin one searchable corpus state for the entire investigation.
4. Prove whether that state was complete enough for positive and negative claims.
5. Retrieve all matching evidence without unbounded payloads or pagination drift.
6. Verify retrieved evidence by stable content digest.
7. Search patch content independently from paths and unrelated activity.
8. Fail visibly whenever the collector requests a constraint the server did not apply.
